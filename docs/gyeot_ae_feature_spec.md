## 1. 서비스 개요

실종 아동·어르신의 골든타임 확보를 위해, 시민의 목격 제보를 실시간으로 수집하고 AI 얼굴 유사도 분석으로 신뢰도를 판별한 뒤, 검증된 제보를 시간순 이동 경로로 지도에 복원하는 서비스.

기존 앰버 경보가 일방향 전달에서 멈추는 것과 달리, **시민의 목격이 보호자에게 되돌아오는 양방향 구조**를 만드는 것이 목표.

### 핵심 루프

```
보호자 등록 → 주변 시민 알림 → 시민 제보(사진) → AI 유사도 분석
   → 검증된 제보를 시간순 연결 → 이동 경로 복원 → 보호자 확인 → 발견
```

## 2. 사용자 역할

역할은 계정 속성이 아니라 **행동에서 파생**된다. 등록한 사람이 그 사건의 보호자, 제보한 사람이 그 사건의 제보자다. 같은 사용자가 두 역할을 모두 가질 수 있다.

| 역할 | 정의 | 로그인 |
|---|---|---|
| 게스트 | 앱 설치 후 기본 상태 | 불필요 |
| 제보자 | 특정 사건에 제보한 사용자 (게스트 포함) | 불필요 |
| 보호자 | 특정 사건을 등록한 사용자 | **필요** |

### 권한 매트릭스

| 기능 | 게스트 | 로그인 사용자 | 사건 보호자 |
|---|:---:|:---:|:---:|
| 실종자 목록·상세 열람 | O | O | O |
| 지도 열람 | O | O | O |
| **제보 작성** | **O** | O | O |
| AI 분석 실행 | O | O | O |
| 내 제보 이력 | 기기 기준 | 계정 기준 | 계정 기준 |
| 실종자 등록 | X | O | — |
| 사건 정보 수정 | X | X | O |
| 제보 숨기기·확인 체크 | X | X | O |
| 발견 완료 처리 | X | X | O |
| 긴급도 올리기 | X | X | O (사건당 1회) |
| 알림 수신 설정 | X | O | O |

**제보를 게스트에 여는 것이 이 서비스의 핵심 설계다.** 목격자는 대부분 우연히 지나가는 사람이고, 회원가입 절차가 제보 자체를 소멸시킨다.

### 하단 네비게이션 (4탭)

`홈` · `실종자` · `지도` · `MY`

실종자 등록은 탭에 넣지 않는다. 평생 한 번도 누르지 않는 것이 최선인 기능이 상시 4칸 중 하나를 차지할 이유가 없다. 대신 **상단 바로가기 띠 + 하단 소개 블록** 이중 배치로 처리한다.

### 진입 흐름

```
스플래시 → (첫 실행) 온보딩 3장 → 홈 [게스트]
```

로그인은 독립 화면이 아니라 **등록·내 사건 관리 시도 시 개입하는 모달**이다. 성공 후 원래 하려던 동작으로 바로 진행하며, 홈으로 되돌리지 않는다.

#### 상단바 전환 임계점

| 구간 | 동작 |
|---|---|
| 0 ~ (사진높이−상단바−60)px | 완전 투명, 흰 원형 버튼 |
| ~ (사진높이−상단바)px | 흰 배경 페이드 인, 원형 버튼 페이드 아웃 |
| ~ (이름 하단−상단바−40)px | 흰 상단바, 제목 없음 |
| ~ (이름 하단−상단바)px | 제목 + 경과 시간 페이드 인 |

값은 하드코딩하지 않고 이름 요소 위치를 런타임 측정한다. 경계 깜빡임 방지를 위해 8~10px 히스테리시스를 둔다.

#### 4-1. 제보 타임라인 상세

```
레일          카드
 ③  ─┐   [썸네일] 오후 5시 12분
     ┆            남동구 만수동 버스정류장
     ┆            ▓▓▓▓▓▓▓▓░░ 82%
     ┆   ⋯ 42분 공백
 ②  ─┤   [썸네일] 오후 4시 30분
     ┆            ↘ 남동쪽 1.4km
 ①  ─┤   ...
 ·  ─┤   [흐림] 확인 필요  34%
 📍 ─┘   오후 2시 40분 · 최초 실종
```

| ID | 기능 | 상세 |
|---|---|---|
| F-3.5.1 | 정렬 | **최신이 위**, 최초 실종이 맨 아래 고정 앵커 |
| F-3.5.2 | 번호 배지 | 지도 핀 번호와 동일. **유사도 40% 미만은 번호 없이 점(·)** |
| F-3.5.3 | 유사도 표시 | 게이지 + 숫자 + 색 3중 표기 (색각 이상 대응) |
| F-3.5.4 | 저신뢰 처리 | 40% 미만은 점선 테두리, 글자 흐림, "확인 필요" 라벨. **삭제하지 않음** |
| F-3.5.5 | 필터 토글 | "유사도 60% 이상만" — 켜면 "3건 숨김" 표시 |
| F-3.5.6 | 제보 공백 | 60분 이상 끊긴 구간을 레일에 "⋯ N분 공백"으로 표시 |
| F-3.5.7 | 이동 방향·거리 | 이전 제보 대비 방위·거리 ("↘ 남동쪽 1.4km") |
| F-3.5.8 | 날짜 구분선 | 날짜가 바뀌면 레일에 삽입 |
| F-3.5.9 | 접기 | 10건 초과 시 상위 5건만 펼침 |
| F-3.5.10 | 실시간 반영 | 새 제보 도착 시 최상단 삽입 + 1.2초 하이라이트 |
| F-3.5.11 | 카드 탭 | 제보 상세 바텀시트 (원본 사진 확대, 등록 사진 대조) |
| F-3.5.12 | 번호 탭 | 지도 탭 이동 + 해당 핀 포커스 |
| F-3.5.13 | 보호자 전용 | 제보별 "확인함" 체크, 숨기기 |
| F-3.5.14 | 신고 | 길게 누르기 → 허위·장난 제보 신고 |
| F-3.5.15 | 제보 0건 | 마스코트 + "공유하면 더 많은 사람이 볼 수 있어요" + 공유 버튼 |

**낮은 유사도를 지우지 않는 이유**: 옷을 갈아입었거나 뒷모습만 찍힌 진짜 제보가 걸러지면 경로에 구멍이 생긴다. 특히 고령자는 얼굴 인식 정확도가 구조적으로 낮다(회색 등산복, 흰머리, 모자).

### S4. 제보창

| ID | 기능 | 상세 |
|---|---|---|
| F-4.1 | 대상 확인 헤더 | 썸네일 + 이름 + 인상착의 요약. 누구를 제보하는지 명시 |
| F-4.2 | 사진 첨부 | 카메라 촬영 / 앨범 선택. 1장 필수 |
| F-4.3 | 위치 자동 첨부 | GPS 좌표 + 역지오코딩 주소. 수동 조정 가능 |
| F-4.4 | 시간 자동 첨부 | 사진 EXIF 촬영 시각 우선, 없으면 현재 시각. 수정 가능 |
| F-4.5 | 사진 분석 | "사진 분석하기" → S4-1 바텀시트 |
| F-4.6 | 제보 버튼 활성화 | **분석 완료 전까지 비활성**. 숨기지 않고 회색 표시 |
| F-4.7 | 이탈 방지 | X 누르면 "작성을 취소할까요?" 확인. 네비바 숨김 |

**시민이 직접 입력하는 항목은 사진 한 장뿐이다.** 입력란을 하나 늘릴 때마다 제보 하나가 사라진다고 본다. P4(배달기사, 신호 대기 40초) 제약이 기준.

**`observed_at`과 `created_at`을 분리해야 한다.** 나중에 사진첩에서 찾아 올리는 경우가 있고, 경로 정렬은 반드시 `observed_at` 기준이어야 한다.

### S4-1. AI 분석 결과 (바텀시트)

| ID | 기능 | 상세 |
|---|---|---|
| F-4.1.1 | 유사도 게이지 | 반원 아크 + 큰 숫자(%) |
| F-4.1.2 | 등급 라벨 | 높음(70%↑) / 보통(40~70%) / 낮음(40%↓) |
| F-4.1.3 | 대조 이미지 | 등록 사진 ↔ 제보 사진 나란히 |
| F-4.1.4 | 위치·시간 재확인 | |
| F-4.1.5 | 안내 문구 | "옷을 갈아입었거나 각도가 달라 낮게 나올 수 있습니다. **확신이 없어도 제보해 주세요. 확인은 보호자가 합니다.**" |
| F-4.1.6 | 얼굴 미검출 | 유사도 산출 불가 안내. 제보는 여전히 가능(`face_found: false`로 저장) |
| F-4.1.7 | 분석 확인 | 제보창으로 복귀, 결과 첨부 완료 상태 |

**별도 화면이 아니라 바텀시트인 이유**: 제보창 입력값이 살아 있는 채로 겹쳐 뜬다. 화면 전환 비용이 0이다.

**이 화면의 목적은 필터링이 아니라 심리적 면죄부다.** 목격자가 신고를 망설이는 가장 큰 이유는 "틀렸을까 봐"이며, 그 부담을 AI가 대신 진다.

**전체 보기에서 경로를 그리지 않는 이유**: 경로는 사건 하나를 선택했을 때 의미가 생기는 정보다. 여러 개를 겹치면 선이 엉켜 아무것도 읽히지 않는다.

## 5. 공통 규칙

### 5.1 긴급도 점수

목록·홈·지도의 기본 정렬 기준. **재등록 버튼 같은 사용자 노동으로 순위를 올리는 방식을 쓰지 않는다.**

```
긴급도 = 골든타임 × 취약도 × 거리 × 제보공백
```

| 요소 | 값 |
|---|---|
| 골든타임 | 0~3h ×3.0 / 3~12h ×2.0 / 12~48h ×1.5 / 48h+ ×1.0 |
| 취약도 | 아동·어르신 ×1.5 / 그 외 ×1.0 |
| 거리 | 3km 내 ×2.0 / 10km 내 ×1.3 / 그 외 ×1.0 |
| 제보 공백 | 마지막 제보 후 1h 경과 ×1.3 |
| 부스트 | 보호자가 사건당 1회 사용 시 ×1.5 (24시간 유효) |

**경과 시간이 길어지면 점수가 자연히 내려간다.** 사용자 조작 없이 새 사건이 올라오고 오래된 사건이 내려간다. 제보가 끊긴 사건은 가중치를 받아 다시 올라온다.

> MVP에서는 `골든타임 × 거리`만으로도 충분히 동작한다.

### 5.2 유사도 등급

| 등급 | 구간 | 색 | 번호 | 타임라인 |
|---|---|---|:---:|---|
| 높음 | 70% 이상 | `#3B6CB7` | O | 기본 |
| 보통 | 40 ~ 70% | `#7FB3FF` | O | 기본 |
| 낮음 | 40% 미만 | `#B3C2D4` | X (점) | 점선, 흐림, "확인 필요" |
| 미검출 | 얼굴 없음 | `#B3C2D4` | X | "얼굴 미검출" |

- **저장 임계값 없음** — 모든 제보를 저장한다
- **경로 포함 임계값 40%** — `route_index`는 40% 이상에만 부여
- **기본 필터 60%** — 지도·타임라인 토글의 기본 상태

### 5.3 경과 시간

- 서버 시각 기준으로 계산해 클라이언트에 전달
- 사용자가 리셋할 수 없다. 사건의 사실이지 상태값이 아니다
- 표기: 24시간 미만 "3시간 12분", 이상 "2일 5시간"

### 5.4 마스코트 곁이

| 등장 | 물러남 |
|---|---|
| 급한 사건이 없는 홈 | 긴급 배너 |
| 제보 완료 | 실종자 등록 폼 |
| 발견 완료 | AI 분석 결과 |
| 온보딩·스플래시 | 지도 이동 경로 |
| 검색 결과 없음 | 사건 상세·제보 타임라인 |

경과 시간 옆에서 웃는 얼굴은 보호자에게 상처가 된다. 캐릭터의 따뜻함은 아껴 써야 힘이 생긴다.

### 5.5 상단바 규칙

| 화면 | 구성 |
|---|---|
| 홈 | 로고(중앙) + 알림 |
| 실종자·지도·MY | 화면 제목(중앙) + 액션 |
| 실종자 상세 | 뒤로 + 이름(스크롤 시) + 공유 |
| 제보창·등록 폼 | 닫기(X) + 제목 |
| **외부 유입 상세** | 뒤로 대신 **작은 심볼** → 탭 시 홈 |

공유 링크로 들어온 사용자는 돌아갈 스택이 없다. 이때만 브랜드를 노출한다.

### 5.6 워드마크

- 로고·앱 아이콘·스플래시: `곁愛`
- 본문·푸시 알림·15px 이하·고령자 안내문: `곁애`

`愛`는 화면 낭독기가 중국어로 읽거나 건너뛴다.

## 6. 데이터 모델 (요약)

전체 스키마는 API 명세서 참조.

```
User          id, kakaoId, name, profileImageUrl, createdAt
Device        deviceHash, pushToken, radiusKm, categories, quietHours
MissingCase   id, guardianId, name, age, gender, category,
              description, height, weight,
              lastLat, lastLng, lastAddress, missingAt,
              status(active|resolved), resolvedAt,
              boostUsedAt, faceEncodings[], photos[], createdAt
Report        id, caseId, photoUrl,
              lat, lng, placeName,
              observedAt, createdAt,
              similarity, faceFound, grade, routeIndex,
              status(visible|hidden|confirmed),
              reporterId|null, deviceHash, flagCount
Analysis      id, caseId, photoUrl, similarity, faceFound, expiresAt
```

### 핵심 설계 포인트

| 항목 | 이유 |
|---|---|
| `observedAt` ≠ `createdAt` | 나중에 올리는 사진 대응. 경로 정렬은 `observedAt` |
| `routeIndex` 별도 필드 | 보호자가 사진을 추가하면 유사도 재계산 → 번호 재부여 필요 |
| `faceEncodings[]` 배열 | 사진 여러 장의 벡터를 모두 저장, 최고 유사도 채택 |
| `deviceHash` | 게스트 제보 남용 방지 + 로컬 이력 |
| `Analysis` 임시 엔티티 | 분석과 제보가 2단계로 분리됨 (TTL 10분) |

## 부록 A. 백엔드 현황과의 차이

현재 `Gyeot-ae-Backend` README 기준으로 디자인이 앞서 있는 항목.

| # | 항목 | 백엔드 현황 | 디자인 요구 | 영향 |
|---|---|---|---|---|
| 1 | **분석·제보 분리** | `POST /report`가 업로드+분석+저장을 한 번에 | "사진 분석하기" → 결과 확인 → "제보" **2단계** | **높음** — 엔드포인트 분리 필요 |
| 2 | 유사도 임계값 | 60% 단일 (`is_match`) | 70/40 3단계, 40% 미만도 저장 | **높음** — 등급 체계 변경 |
| 3 | 실종자 필드 | name, description, last_lat/lng, photo | + 나이, 성별, 구분, 실종일시, 신체, 연락처, **사진 다중** | 중 |
| 4 | 시간 필드 | `reported_at` 단일 | `observed_at` / `created_at` 분리 | 중 |
| 5 | 목록 API | `GET /missing` 전체 반환 | 검색·필터·정렬·거리·페이지네이션 | 중 |
| 6 | 긴급도 | 없음 | 점수 계산 및 정렬 | 중 |
| 7 | 인증 | 없음 | 등록만 로그인, 제보는 게스트 | 중 |
| 8 | 발견 완료 | `status` 필드만 존재 | 전환 API + 목록 유지 표시 | 낮음 |
| 9 | 위치명 | 없음 | 역지오코딩 주소 | 낮음 |
| 10 | 알림 | 없음 | 반경 기반 푸시 | 낮음 |
| 11 | 제보 관리 | 없음 | 숨기기·확인·신고 | 낮음 |

### 유지해도 되는 것

- `face_recognition` 128차원 벡터 + 유클리드 거리 방식
- `path` 배열을 시간순 정렬해 반환하는 구조 (폴리라인에 그대로 사용)
- JSON 파일 DB (해커톤 범위)
- Firestore 실시간 푸시 (선택)
- `GET /uploads/<filename>` 사진 서빙

### 1번 항목이 가장 중요하다

디자인상 시민은 **분석 결과를 보고 나서 제보 여부를 결정**한다. 현재 구조로는 제보가 이미 저장된 뒤에 결과를 보게 되어, "취소" 버튼이 의미를 잃는다. `POST /reports/analyze`(임시 분석)와 `POST /reports`(확정 저장)로 나누고, 분석 결과를 10분 TTL로 보관하는 방식을 권한다.
